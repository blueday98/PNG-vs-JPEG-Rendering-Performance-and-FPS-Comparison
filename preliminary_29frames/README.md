# OpenCV 프레임 저장 형식 및 HPE 예비 검증 기록

> 상태: 29장 예비 검증과 이상치 시각 확인까지 완료. 255장 전체 HPE·최종 피처 검증은 아직 수행하지 않았다.
>
> 작업 기준: WSL Ubuntu의 `/home/jwp/Oracle_Project2/Oracle_Project/PoC`. 이 문서는 기존 프로젝트 README와 별개인 실험 기록이다.

## 1. 목표

러닝 영상의 프레임 이미지를 반드시 저장하는 조건에서 OpenCV(cv2)의 처리 시간을 줄일 수 있는지 확인했다. JPEG 저장이 빨랐으므로, 손실 압축이 Halpe26 출력에 미치는 영향을 추가로 예비 비교했다. 모델 구조나 학습을 변경한 실험은 아니다.

## 2. 프레임 추출 속도 조사

- 영상: 재혁님 달리기 영상 `run/speed_test/output_h264.mp4`.
- 추출 수: 각 방식 모두 255장.
- 비교한 PNG와 JPEG 해상도: 모두 1920×1080.
- JPEG 품질 95는 해상도 축소 설정이 아니라 손실 압축 품질 설정이다.
- 시간은 셸 `time` 출력의 `total`(실제 경과 시간)을 사용했다.

| 방법 | 저장 형식 | 시간 | 저장 용량 |
|---|---|---:|---:|
| OpenCV | PNG | 17.687초 | 902MB |
| OpenCV | JPEG 품질 95 | 3.072초 | 186MB |
| FFmpeg | PNG | 10.022초 | 498MB |
| FFmpeg | JPEG `-q:v 2` | 1.088초 | 122MB |

핵심 비교는 **OpenCV를 유지하고 PNG에서 JPEG 품질 95로 바꾼 경우**다. 관측된 경과 시간은 약 82.6% 감소했고, 약 5.76배 빨랐다. 용량은 약 79.4% 감소했다.

주의:

- 단일 영상의 초기 측정값이며 반복 평균이나 캐시·부하를 통제한 벤치마크는 아니다.
- OpenCV PNG 실행은 프레임 255장을 저장한 뒤 `outputs/details.json`의 부모 폴더가 없어 종료 단계에서 오류가 났다. 17.687초는 그 실패까지 포함한 경과 시간이며, 전체 스크립트 정상 완료 시간이라고 표현하면 안 된다.
- FFmpeg `-q:v 2`와 OpenCV 품질 95는 같은 품질 척도가 아니다. 두 JPEG 결과를 동일 품질의 순수 라이브러리 속도 비교로 해석하지 않는다.
- 파일 용량은 `du -sh` 표시값이다. 관측한 속도 개선은 프레임 추출·저장 단계이며 서비스 전체가 5.76배 빨라졌다는 뜻이 아니다.

## 3. 29장 예비 검증 준비

전체 255장 중 `1, 10, 19, …, 253`번을 9프레임 간격으로 선택했다. PNG/JPEG 각각 29장이며 같은 번호끼리 비교했다.

| 구분 | 위치 (`PoC` 기준) |
|---|---|
| 전체 PNG | `run/speed_test/opencv_frames/` |
| 전체 JPEG 품질 95 | `run/speed_test/opencv_jpg/` |
| 기존 검출 기준 0.3 표본 | `run/hpe_compare/{png,jpeg}/inputs/` |
| 최신 검출 기준 0.4 표본 | `run/hpe_compare_04/{png,jpeg}/inputs/` |
| 각 실험의 HPE 출력 | 해당 형식 폴더의 `outputs/pose_predictions.json` |

모델 설정은 RTMDet-nano(320×320), RTMPose-M Halpe26(입력 너비 288×높이 384), ONNX Runtime, CPU다. NMS 기준은 0.45이며, 검출 점수 기준만 0.3과 0.4로 구분했다.

기존 HPE 스크립트는 PNG만 읽으므로 이미지 목록을 다음처럼 바꿨다.

```python
image_paths = sorted([
    *INPUT_ROOT.glob("*.png"),
    *INPUT_ROOT.glob("*.jpg"),
])
```

실행은 시스템 Python이 아닌 프로젝트 가상환경을 사용한다. 최신 예비 실험에 사용한 명령은 다음과 같다.

```bash
cd ~/Oracle_Project2/Oracle_Project/PoC
.venv/bin/python -m scripts.hpe.hpe_model . hpe_compare_04/png --device cpu
.venv/bin/python -m scripts.hpe.hpe_model . hpe_compare_04/jpeg --device cpu
```

이 예비 실험의 `details.json`은 HPE 코드가 참조하는 너비만 포함한 `{"video":{"width":1920}}`이다. FPS·영상 높이 등을 참조하는 후속 피처 계산에는 원본 영상에서 얻은 완전한 메타데이터가 필요하다. 다른 영상의 `details.json`을 가져다 쓰면 안 된다.

## 4. 비교 방법

- JSON의 `image_path`에서 확장자를 뺀 프레임 번호로 대응시켰다.
- 각 프레임에서 `track_id=0`인 사람의 원시 키포인트를 비교했다. 이는 최신 피처 코드의 `people[0]` 선택과 다를 수 있으므로 HPE 비교를 최종 피처 검증과 동일시하지 않는다.
- 같은 인덱스 키포인트의 유클리드 거리 `sqrt((x_png-x_jpeg)^2 + (y_png-y_jpeg)^2)`를 픽셀 단위로 계산했다.
- 평균, 95백분위, 최대값과 신뢰도 점수의 절대 차이를 확인했다.
- 기본 통계에는 낮은 신뢰도의 점도 포함했다. 정답 좌표가 없으므로 이는 **두 출력의 차이**이며, 실제 위치에 대한 정확도 오차가 아니다.

## 6. 모델 담당자 수정 반영: 0.3 → 0.4

로컬 수정 사항을 stash에 보관한 뒤 `git pull --ff-only`로 `42f86dc → 9a3df7a` 업데이트했다. 이 커밋 간 `hpe_model.py` 변경은 검출 점수 기준 `score_thr=0.3 → 0.4`였다. 이후 JPEG 읽기 부분만 다시 추가해 새 폴더에서 실행했다. 기존 stash를 통째로 복원한 것은 아니다.

이 변경은 낮은 점수의 검출을 줄이는 조정이지, 반사상을 의미적으로 구분하는 기능은 아니다.

| 항목 | 기준 0.3 | 기준 0.4 |
|---|---:|---:|
| 형식별 입력 | 29장 | 29장 |
| 형식별 JSON 저장 / 공통 비교 | 11장 | 10장 |
| 한쪽에만 저장된 프레임 | 0장 | 0장 |
| 평균 좌표 차이 | 1.844px | 1.929px |
| 95백분위 좌표 차이 | 3.707px | 3.905px |
| 최대 좌표 차이 | 165.100px | 165.100px |

0.4 결과에는 기존 11장 중 244번이 없고 나머지 10장이 양쪽에서 동일하게 저장됐다. 244번은 기존 시각 확인에서 유리 반사상을 추적한 장면이었다. 다만 **이 한 장이 빠졌다고 모든 반사상이 제거됐다고 결론 낼 수 없다.** 0.4에서 제외된 19장의 사유별 수량을 0.3의 분류와 혼용하지 않는다.

평균이 1.844에서 1.929로 변한 것은 비교 프레임 집합 자체도 바뀐 결과다. 이 수치만으로 검출 기준 0.4가 더 나쁘다고 해석할 수 없다.

## 7. 최대 165.1px 차이를 직접 그림으로 확인

최대 차이는 두 기준 모두 **235번 프레임의 왼쪽 귀(키포인트 인덱스 3)**에서 발생했다. 인덱스는 프로젝트 `utils.py`의 Halpe26 정의 및 [MMPose Halpe 정의](https://github.com/open-mmlab/mmpose/blob/main/configs/_base_/datasets/halpe.py#L28-L34)와 대응한다.

| 항목 | PNG | JPEG 품질 95 |
|---|---:|---:|
| x 좌표 | 376.243px | 375.257px |
| y 좌표 | 322.891px | 487.988px |
| 신뢰도 점수 | 0.4491 | 0.5732 |
| 코드의 0.5 기준 observed | false | true |

최신 0.4 결과의 두 귀 좌표를 같은 PNG 배경 위에 표시해 사용자가 Cursor에서 직접 확인했다. 하늘색은 PNG, 주황색은 JPEG, 빨간 점선은 두 점 사이의 거리다.

![사용자가 확인한 0.4 기준 235번 프레임](results_04/frame235_comparison.png)

실제 러너는 화면 왼쪽으로 벗어나 머리가 잘렸는데, 두 귀 추정점은 유리문 쪽에 찍혔다. 따라서 **PNG가 정확하고 JPEG만 165px 틀렸다는 의미가 아니다.** 제대로 보이지 않는 귀에 대해 두 예측이 크게 달라진 실패 사례다.

기존 0.3 결과에서는 235번의 첫 검출 박스가 반사상이고 추적 대상은 화면 밖으로 잘린 실제 러너였다. 가장자리 검사는 첫 박스만 보므로 실제 추적 대상의 잘림을 통과시켰다. 244번에서는 반사상 자체가 추적 대상으로 선택됐다.

## 8. 압축 영향과 검출 박스 영향을 구분한 추가 검사

이 검사는 기존 0.3 결과의 235번 이상치를 대상으로 수행했다.

| 검사 | 결과 |
|---|---|
| PNG 29장을 품질 95 JPEG로 재인코딩하고 기존 JPEG와 디코딩 픽셀 비교 | 29쌍 모두 정확히 일치 |
| 같은 PNG·같은 박스로 포즈 반복 추론 | 모든 점의 차이 0px |
| 기존 PNG/JPEG 좌표 각각 재현 | 각 저장 결과와 차이 0px |
| PNG/JPEG에 동일한 PNG 박스 사용 | 귀 좌표 차이 164.987px 유지 |

프레임 시점이 어긋난 비교는 아니며, 검출 박스 차이만으로 생긴 이상치도 아니다. **이 불안정한 장면에서는 JPEG 입력의 픽셀 변화에 포즈 출력이 크게 달라질 수 있음**을 확인했다. 모델 내부의 상세 원인이나 어느 좌표가 정답인지는 이 검사로 판단하지 않았다.

참고로 0.3 결과에서 양쪽 점수가 모두 0.5 이상인 271개 점만 비교하면 평균 1.201px, 최대 8.478px였다. 이는 보조 분석일 뿐이다. JPEG의 문제 귀 점은 0.5를 넘었으므로 신뢰도 기준만으로 모든 잘못된 추정을 막을 수 없다.

## 9. 현재 결론과 다음 검증

> OpenCV를 유지하면서 PNG를 JPEG 품질 95로 바꾸면 이번 영상에서 프레임 추출·저장 시간이 크게 줄었다. HPE 예비 비교에서는 출력 차이가 확인됐고, 최대 165.1px 차이는 화면 밖으로 잘린 러너의 귀 추정에서 발생했다. 최신 검출 기준 0.4에서도 해당 차이는 남았다. 따라서 속도 개선 가능성은 확인했으나, 아직 JPEG 적용의 최종 적합성이 검증된 것은 아니다.

> 당시 HPE 코드가 width만 사용해서 최소 정보로 실행한 것이다.
원래 전체 형식은 extract_frames.py가 영상 정보를 읽어 생성한다다. 이번에는 이미 추출한 이미지만 비교 폴더로 복사했기 때문에 그 생성 과정을 생략했다.
255장 전체 검증에서는 원본 영상에서 메타데이터를 읽어 정식 details.json을 만들어 사용하겠다. 특히 피처 계산에는 FPS와 높이 등의 정보도 필요하다.

다음은 같은 영상의 255장을 연속 입력하는 전체 검증이다.

1. PNG/JPEG 프레임 대응과 모델·런타임·임곗값을 동일하게 유지한다.
2. 255장 각각의 검출·제외·처리 중단 상태를 기록한다. 입력 255장이 모두 HPE JSON에 남는다고 가정하지 않는다.
3. 실제 러너의 전신이 보이는 구간과 화면 잘림·반사상 구간을 구분한다. 실패 장면도 삭제하지 않고 별도 결과로 보고한다.
4. 키포인트, 신뢰도, 최종 피처의 차이를 비교한다. 허용 차이는 모델 담당자와 합의한다.
5. 결론은 이 영상·모델·JPEG 품질 조건에 한정한다. 정답 주석이 없다면 '출력 차이'를 '정확도 저하'라고 표현하지 않는다.

29장 표본은 9프레임 간격이어서 연속 영상과 추적 상태·20프레임 조건의 의미가 다르다. 이 표본으로 cadence나 IC/TO 등 시간 기반 피처까지 검증했다고 말할 수 없다.
